# P1 法律 Skills 选品计划

本计划服务冻结的 P1（2026-10-20 至 2026-10-28）30–50 个结构化法律 Skills 目标，不改变路线图、排期或验收口径。以下为 P0 的 10 条候选选品基线；LR-P1-01 于 2026-10-17 新增 10 条，联合初筛共 20 条候选记录，正式目录仍为 0。新批次 A3/C7/B0、证据与责任见 [批次审核表](P1_BATCH_01_REVIEW.md)；下述既有 A3/C7/B4 和七条阻塞保持历史状态。没有 30–50 条正式入库成果，也不设三轨数量配额。执行规则见 [收录政策](SKILL_INTAKE_POLICY.md)，原始审计见 [P1_READINESS.md](P1_READINESS.md)，逐条可机读提案见 [p1-proposals.json](../data/intake/p1-proposals.json)。

## 六类覆盖与优先顺序

以下方向是发现和需求访谈范围，不是已存在或已通过专业核查的 Skills。按实际候选价值、许可和专业资源动态安排，不能以类目最低数量冲淡质量门槛。

| 业务类 | 现有基础与缺口 | P1 发现 / 独立需求方向 |
| --- | --- | --- |
| 合同审查 | 有 3 条 A 优先考察提案，其中法律顾问为多类入口；未完成专业复核 | 先审查一般合同、委托律师合同的独立性及适用边界，再寻找履行、解除、特定交易类型等可区分工作流 |
| 民商事诉讼 | 3 个相关候选均阻塞；套件导航不能当实体流程扩容 | 从请求权、举证、庭前材料等业务问题访谈，寻找独立且权利清楚的入口；评估原创证据规划机会 |
| 公司并购 | 唯一经营者集中候选许可冲突；不能代表完整并购覆盖 | 发现尽调、交易材料和公司决议等独立工作流；经营者集中资料采集可提出原创需求，法律结论仍由专家负责 |
| 企业合规 | 法律顾问 A 提案有相关分类；经营者集中阻塞 | 按公司治理、劳动及数据等场景逐项发现和核查；不把宽泛“合规”标签算多个能力 |
| 刑事/行政 | 3 个相关候选均阻塞，行政入口不证明刑事能力 | 分别寻找刑事程序与行政救济入口；评估行政救济事实/期限核对的原创需求，刑事复杂场景优先补独立专业资源 |
| 法律检索 | 法律顾问为多类入口；CN Law Hub 与爽律授权仍阻塞 | 优先找法规出处、版本与引用核对工作流，评估原创来源追溯需求；纯数据库/API/MCP 不纳入 Phase 1 Skills 数量 |

## 独立原创机会（均仅提议）

以下 4 项使用新 ID，第三方候选不被改为原创、不继承其许可或审批。每项预期交付均包含独立需求、设计和测试证据；是否进入研发由 Human Maintainer 后续决定。本任务不输出完整 Skill，不提供受限全文给模型。

这些是条件性可行性建议；当前授权阻塞不等于已经证明必要授权永远无法取得。立项前先比较许可补证、已有获授权替代入口、实际业务缺口与研发成本；必要授权无法取得且独立需求仍有价值时，再决定原创研发的必要性。

| 机会 ID / 问题 | 预期交付 | 独立设计来源及验收重点 |
| --- | --- | --- |
| original-litigation-evidence-plan：实务人员需要把案件事实、待证事项与证据缺口关联 | 独立需求说明、事实与证据输入/输出契约、人工核对边界、合成案件测试设计；后续获批才实现 | 独立访谈、民事诉讼法及证据规则的官方文本；独立设计对应矩阵，测试缺证/矛盾与人工升级，不沿用诉讼套件或 CorpClaim 结构/模板 |
| original-merger-intake：经营者集中初筛前资料不齐导致人工复核困难 | 资料采集需求、事实缺口提示设计、专家交接清单和合成测试计划；不自动生成申报法律结论 | 独立并购业务访谈、反垄断法与申报标准官方文本；测试控制关系资料缺失、复杂结构交专家；不使用冲突许可候选的阈值表、决策树或提示词 |
| original-admin-remedy-intake：行政救济需要可靠记录行为、送达及程序事实 | 原创事实采集与待核期限清单设计、人工确认节点和合成边界案例计划 | 独立行政业务访谈、行政复议法/行政诉讼法及官方解释；核对前置程序、送达和期限不确定性，不复刻 W0–W4 或套件模块 |
| original-legal-source-trace：引用缺少法规版本、出处及适用时间证据 | 原创引用记录契约、官方来源核对步骤设计、冲突/缺源提示和独立测试计划 | 独立法律检索需求、国家法律法规数据库等官方公开文本与发布记录；分别核对文本使用条款，只设计工作流，不建设 API/MCP 或爬虫，不复制 CN Law Hub 组件 |

负责人：Human Maintainer 批准需求、人员与资源，工程维护者保留独立设计/实现/测试来源，法律专业人员确定专业边界及法规适用。若第三方资料接触造成独立性风险，先完成来源披露与隔离设计再开发。刑事工作流仍需单独发现与专家访谈，不把上述行政机会充当刑事覆盖。

## 扩充、去重与成本

先从已有 Awesome-LegalSkills-CN 线索和原作者公开发布入口开展有限、可复核发现，记录检索范围、日期、固定提交及失败情况，逐项按 DISCOVERY_PROTOCOL 入候选。扩大到不同载体时核对真正独立工作流；聚合目录、搜索摘要只提供线索。C 采用原链接和独立元数据，不批量复制全文、不自动安装执行。只有三轨各自完成正式门槛的独立条目才能计入 30–50；数量不足时公开缺口和阻塞，请维护者安排补证与复核资源，不虚构已核实条目或自行改变冻结目标。

同源镜像、改名、翻译及多宿主重复交付先合并为一个能力对象；语言版本仅在有实质独立用途与证据时另议。套件默认计一个可辨识入口；拆分须逐子项证明独立输入/任务/输出、固定入口、文件许可范围与专业时效证据，保留父子来源关系，由 PR 说明计数依据。多业务标签不重复计数；原创解决同类问题须说明独立需求和与现有目录的用途差异，不靠换 ID 增加数量。

| 模式 | 授权与工程成本 | 专业与持续维护成本 |
| --- | --- | --- |
| A | 最高的材料清单、贡献者/依赖权利核对、分发声明和版本维护；现有 MIT/Apache 标签不消除此成本 | 全部法律依据与场景复核，版本更新和法规变化均触发复审；先考察 3 条，不承诺全部可托管 |
| B | 独立访谈、设计隔离、原创来源证明、实现与测试资源；不因第三方受限而自动变得便宜 | 从零建立专业验收依据；P1 可先完成可行性和需求设计，完整实现仅在独立授权及资源足够时开展 |
| C | 链接/版本、独立摘要和拟索引用法审查，减少全文分发义务；许可限制仍需保留 | 正式目录所需法域与时效复核仍完整适用；链接失效与上游变化需跟进，无依据不估算工时 |

## P1 执行窗口与待批事项

1. 10.20–10.22：维护者选择 3 条 A 的具体托管范围、指派专业复核；工程维护者整理材料边界并继续六类发现；7 条阻塞逐项决定补证或继续候选索引，新增证据须重审。
2. 10.23–10.25：按实际许可及专家产能分批复核，独立 P1 PR 提交满足八字段要求的条目；对 4 项原创机会做需求与成本可行性审查，不以计划表示实现完成。
3. 10.26–10.28：去重、复查固定版本和许可变化、检查专业证据及真实法规时效、CI 和逐项交接；列出实际入库数、候选数及未决缺口，请 Human Maintainer 验收。正式测评、评分、榜单与路由不属于本选品工作。

待 Human Maintainer 后续批准：具体托管材料和使用范围、专业复核人员/资源、七条阻塞的补证或放弃路径、必要的权利人联系及许可接受、原创机会立项与隔离方案、未来证据化审批记录及托管目录设计。三轨产品决策已获批准，本 PR 不要求重新批准该决策；本 PR 合并也不代表批准任何全文托管、原创完整研发或 P0/P1 自动验收。
