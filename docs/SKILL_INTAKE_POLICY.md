# Skills 三轨收录政策 v1

本政策落实 Human Maintainer 在 [LR-P0-04](daily-specs/LR-P0-04.md) 确认的 Phase 1 产品决策，服务 [冻结路线图](../ROADMAP.md) 的 P1 目录整合。三轨是内容取得与交付方式，不是质量等级、测评结果或推荐。当前仅建立规则与提案，不复制第三方全文、不开发完整法律 Skill、不安装或执行上游内容、不开展法律测评或路由。

## 三轨与权限

| 轨道 / 机器值 | 适用条件与交付 | 权限边界 |
| --- | --- | --- |
| A — Curated Hosting / `curated-hosting` | 实务价值明确、可维护的第三方能力；固定完整材料清单后，复制、再分发及拟议用途均有有效授权，完成法律专业复核，才可申请托管全文 | 保留原许可证、版权、署名、NOTICE、修改标记及来源；不得统一改为 LexRouter MIT。根许可不当然覆盖贡献者、依赖、外部笔记、知识库、数据及品牌 |
| B — Original Development / `original-development` | 需求价值高且必要授权无法取得时，可提出独立研发任务；须另有原创标识、需求、设计、实现及测试证据 | 自主原创代码使用已批准的 MIT；不得复制、翻译、改写、从受保护内容抽取结构后重构，或向生成式模型提供未经授权的第三方完整 Skill 来变相复刻。独立开发不继承第三方授权 |
| C — External Reference / `external-reference` | 符合范围但未获托管批准的其他能力，以原始链接、固定版本与独立撰写元数据索引 | 不复制未经授权的完整内容。链接不授予运行、测评、改编、复制或再分发权；外部索引也需来源、描述、法域与时效审查，未满足正式要求仍留候选区 |

原创机会不是第三方候选的状态转换：原候选及其阻塞保留，另建 `original-…` 机会 ID；正式研发时另分配 LexRouter Skill ID、原创仓库来源 URL，不冒充原项目、维护者或其衍生认证。关联候选 ID 仅解释业务缺口，不作为设计材料或许可来源。

## 精选托管筛选与授权证据

托管优先级按以下可核查问题提出，由 Human Maintainer 决定；热度、自报认证、作者头衔、宿主名称和自身评分不能代替判断，也不发布分数。

1. 是否解决中国大陆明确的高频法律任务，有可辨识的输入、工作步骤、输出和人工升级边界。
2. 是否较现有目录提供独立用途，能与套件导航、镜像和翻译副本区分；不存在用子技能数量凑数。
3. 是否能定位固定版本入口、完整材料范围及依赖，具有可阅读文档、错误限制和维护路径；隐含本机路径、工具依赖及安装说明差异须先处理。
4. 法律专业人员能否核对具体法规、适用事实、引用、现行/废止/过渡规则及输出风险；是否提供可由专家审阅的脱敏或合成场景。
5. 能否承担更新、复核、撤回和许可义务。可复制、可运行、可测评、可商用、可改编、可再分发须分别判断。

任何全文进入仓库前，工程维护者须提交材料清单（文件、原路径、固定 commit、blob/hash、依赖与外部材料边界），以及该版本 LICENSE/NOTICE/入口声明的证据引用。许可复核须确认授予主体及范围、贡献者链条、拟使用方式、署名和分发条件、冲突与附加限制；必要时由 Human Maintainer 取得书面许可。书面材料须记录覆盖文件/版本/用途/期限及限制，敏感内容保存在受控位置，公开 PR 仅提供可审查的脱敏结论和定位，不公开私人通信。

`authorization.verified` 或 readiness 的 `clear` 只证明原审计范围，不能推定整包托管批准。许可缺失、冲突、受限或范围不清时保留阻塞；不得择宽解释、把公开访问当授权，或代 Human Maintainer 联系权利人和承诺条件。

## 原创独立性与法律专业复核

原创任务先由 Human Maintainer 确认业务问题、范围与资源。需求来自独立访谈/实务问题与公开官方法规，设计记录列明实际采用的来源、取得方式和权利边界；受限第三方候选只作为机会背景，不作为需求逐句转写或设计模板。记录参与者是否接触过受保护材料；存在接触或相似性风险时交维护者与法律人员确定独立需求/设计人员和隔离措施，再决定是否推进，不能仅凭“原创”自述消除风险。

实施 PR 须包含独立需求、原创设计及演进记录、代码来源和依赖许可、独立编写的合成/脱敏测试及结果、与业务需求对应的验收证据。不得从原 Skill 复制测试、提示词、输出模板或知识库；不得以模型重写充当独立创作。原创提案通过不代表实现已完成或法律质量已通过。

三轨正式条目都须由具备相应专业能力的法律人员完成具名可追溯复核：对象/固定版本、目标场景、CN-Mainland 法域、适用法规及官方现行文本、生效/废止/修订/过渡规则、引用定位、局限、截至日期、结论和待办，并由 Human Maintainer 审核。按 LR-P0-03 的逐候选 `professional_review.required_checks` 交接；尚未指定人员不得写成已复核。法规时效必须有实际核对依据；来源核查日、提交日及模型知识截止日不能用作 `regulatory_as_of`。无法完成者继续留在候选区，不能为达到 30–50 数量填造日期。

## 状态与门槛

以下为独立事实轴，不以单一线性“通过”覆盖全部状态；权限审查和法律复核可并行，正式收录必须汇合所需门槛。

| 事实 | 证据及状态 | 转换条件 / 负责角色 |
| --- | --- | --- |
| 发现候选 | candidates 的 candidate / needs-evidence / rejected | 工程维护者按发现协议核查；仅发现不代表收录 |
| 收录模式提案 | 本次提案 `proposed`，A/B/C | 独立说明价值与模式，由 Human Maintainer 选择范围；不是托管批准 |
| 授权审查通过 | 后续针对指定材料、版本、用途的独立审批记录 | 法律许可复核证据与 Human Maintainer 确认；B 另核原创来源，不继承第三方状态；C 的索引审查不授予执行权 |
| 法律专业审查通过 | 后续独立专业记录 | 法律人员完成上述复核，确认真实法域与法规时效；不得在 P0 readiness 快照伪造完成状态 |
| 正式目录收录 | 当前 `not-admitted`；后续独立 P1 PR | 通过相应许可/原创性门槛、专业门槛、八字段 Schema、目录去重、工程检查及 Human Maintainer 审核合并；A 另须全文托管范围批准 |
| 测评通过 | 当前 `not-performed` | 后续获授权的测评、运行权限及 EVAL_PROTOCOL 独立证据；目录收录不等于测评通过 |
| 路由推荐 | 当前 `not-assessed` | 后续路线图任务、适用范围及测评证据审查；A/B/C 不自动获得推荐资格 |

模式调整必须保留原提案和 PR 历史，注明原因、版本、权限差异及复核范围。A 未获批准可保留 C 提案，但 C 也不能绕过正式目录门槛；A/C 不能通过改为 B 消除原阻塞。被拒绝、暂停或撤回对象保留可公开的原因和 ID，防止被重新发现后静默升级。

## 来源变化、许可变化与退出

工程维护者在每次拟收录、版本更新及使用范围扩展前重新核对来源与许可；P1 结束前逐项复核未决清单，此后复核频率由 Human Maintainer 按风险安排。失效链接、贡献者权利异议、撤回授权通知、许可证变动、法规更新或专业问题触发事件记录和重新审查，不自动跟随上游 HEAD，也不把新许可追溯套用旧版本。

记录触发时间、受影响 Candidate/Skill ID、原版本和新证据、许可与法律影响、负责角色及处置 PR。出现可信授权或法律风险时先暂停新的复制、分发、安装、测评及推荐；Human Maintainer 会同法律人员判断既有许可效力、是否下架托管文件、修正索引/描述、通知已发布渠道或改用明确授权版本。保留允许保留的证据、必要声明及撤回说明，不能继续公开争议全文作为“审计备份”。原授权是否可撤销及既有副本处理须逐案判断，不自行宣称全部权利自动失效或永久有效。恢复须有新证据、相应复核及独立 PR，不能只改状态。

## 最小数据与目录设计

正式 [skill.schema.json](../schemas/skill.schema.json) 八字段及 `skills/<id>/metadata.json` 不变。原候选和 [p1-readiness.json](../data/discovery/p1-readiness.json) 不改、不重复复制证据，新建 [data/intake/p1-proposals.json](../data/intake/p1-proposals.json)：

- `records` 恰好覆盖每个现有 Candidate ID：提议模式、独立选择理由、授权依据引用、审批状态、门槛和责任动作。
- `readiness_snapshot_sha256` 使用已有 fingerprint 算法绑定整条审计记录；经 Candidate ID 查找原记录的 authorization_review、professional_review、blockers，不重复存储许可正文、URL、日期和阻塞证据。摘要变化必须重新审阅提案，摘要不是权属证明。
- `original_opportunities` 使用独立机会 ID、B 模式、业务问题、预期交付、独立设计来源、审批门槛及责任人；`related_candidate_ids` 仅为背景关联，权限固定 `not-inherited`，没有完成实现、复制或再分发许可。
- 所有机器状态仅表达 P0 提案，不能填 approved、正式托管批准、专业通过、已入库、可复制或可再分发。未来审批记录建议按 Candidate ID 或正式 Skill ID 关联，另列精确范围、具名审核者、日期、证据和决策历史；该长期审批契约及托管包目录须另提设计经审核，本次不实施数据库、目录迁移或新 Schema 字段。

记录契约由 `scripts/validate_intake_plan.py` 的 jsonschema 定义，复用 LR-P0-03 校验，不重做候选审计。CLI 与正反测试见 [P1_SELECTION_PLAN.md](P1_SELECTION_PLAN.md)。任何非正式元数据 JSON 均不得放进 `skills/`，因为现有校验器递归识别全部 JSON。
